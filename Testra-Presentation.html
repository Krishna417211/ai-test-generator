01 · The problem

Websites break quietly. Somebody has to keep clicking.

Imagine a big toy shop. Every morning someone must check that every door opens, every button beeps, and every price tag is right. Doing that by hand takes hours — and one tired morning, they miss the broken door.

That checking is called end-to-end (E2E) testing. Real teams write it as code: a robot opens the website, clicks #login-btn, types a password, and confirms the dashboard appears. It is genuinely valuable and genuinely tedious, so it is the first thing teams skip.

Cost

Days per suite

Writing tests for a mid-size app by hand is a multi-day job, repeated whenever the UI changes.

Skill

Specialist knowledge

Good tests need Page Object Models, stable locators, CI wiring — not just "click here".

Trap

AI that invents

Ask a chatbot for tests and it happily writes #submit-button — a button that never existed.

Decay

Brittle locators

div > div:nth-child(3) works today and shatters the moment someone adds a wrapper.

02 · The idea

Testra reads your code, then writes the checking robot for you.

You give Testra the address of your project. It reads the pages like a careful new teammate, notices every button and box that a person could touch, and writes the little robot that will click them all — forever, for free, in seconds.

In

A GitHub URL or a ZIP

Public repo, private repo (signed in with GitHub), or a folder you drag in.

Out

A runnable suite

Page Object Model classes, spec files, config, dependency manifest, and CI pipelines — zipped or pushed straight to a new repo.

Proof

Evidence, not vibes

Every selector is traced back to the line of source it came from, and graded for how likely it is to break later.

05 · Stage one

Before any AI runs, a cheap filter does the boring work.

A big project is like a whole school. Testra only wants the rooms children walk into — not the boiler room, not the store cupboard. It walks the corridors first and marks the doors worth checking.

services/file_extractor.py is 658 lines of pure, local, no-cost logic. It keeps only browser-facing files, detects the tech stack (React, Vue, Next, Nuxt, Angular, Svelte, Django, Flask, FastAPI, Rails, Laravel and their template engines), scores every surviving file 1 to 10 for importance, and fits the winners into a 600,000-token budget.

When the repo overflows the budget, low-scoring files are summarized — ids, classes and routes extracted — rather than dropped. The model keeps its context; it just loses the prose.

06 · Why that isn't enough

Those rules are good guesses. They are also frozen forever.

The ladder says pages/ is a 9 and components/ is a 6. But in this codebase, the pages may be thin two-line shells and every real button may live in features/. A hand-written rule can never notice that, because it only ever looks at the path — never at what is actually inside the file.

Rules only see the name

pages/About.tsx → 9

Forty words of static text. Nothing to click. Nothing a test could ever assert. Still scored 9 and sent to the model at full length.

The body tells the truth

features/Checkout.tsx → 6

Three forms, nine inputs, a data-testid on every control. The single most testable file in the repo — ranked below the About page.

So Testra learns instead of guessing. It looks inside each file, counts what it finds, and trains a small model to predict: would a test ever actually target this file?

07 · Logistic regression · the idea

A machine that answers one yes-or-no question, with a number.

Think of a scorecard for choosing a football team. "Can they run fast?" — add 3 points. "Can they kick?" — add 4. "Do they get tired quickly?" — take away 2. Add it all up, and if the total is high, you pick them.

Logistic regression is exactly that scorecard, with one extra trick: at the end it squashes the total into a number between 0 and 1, so it reads as a confidence rather than a random score. 0.9 means "almost certainly yes". 0.1 means "almost certainly no".

And the points on the card aren't chosen by a person. The machine works them out itself from examples — that is the "learning" part.

08 · Step 1 of 4 — features

Turn a messy file into 17 plain numbers.

A model cannot read code. So extract_features() converts every file into exactly seventeen numbers, each between 0 and 1. Some are yes/no (1 or 0). Some are counts, squashed into range so one enormous file can't dominate. No parsing, no LLM, pure regex — microseconds per file.

The FEATURES list is the contract: the weight vector is aligned to its order, so adding a feature means retraining.

09 · Step 2 of 4 — the maths

Multiply, add, squash.

Each of the seventeen numbers gets multiplied by its own "how much does this matter" number, called a weight. Add them all together, plus one starting number called the bias. That gives you z — which could be anything, like −4 or +9.

Then the sigmoid function bends that raw total onto a 0-to-1 line. Very negative → near 0. Zero → exactly 0.5. Very positive → near 1. That curve is what turns a scorecard into a probability.

def predict_proba(self, features):
    z = self.bias + sum(
        self.weights[f] * features[f]
        for f in FEATURES
    )
    return 1.0 / (1.0 + math.exp(-z))   # σ(z)

Finally the probability is mapped back onto the 1–10 scale the rest of the app already speaks: round(1 + p × 9). p=0.92 becomes a 9. p=0.06 becomes a 2.

10 · Step 3 of 4 — learning

Gradient descent: guess, measure the miss, nudge, repeat.

Playing "warmer, colder". The model starts with every weight at zero — it knows nothing. It guesses. We tell it how wrong it was. It nudges every weight a little in the direction that would have been less wrong. Then it does that 400 times.

  • err = prediction − truth. Guessed 0.8 on a file that should be 1? The miss is −0.2 — a small nudge. Guessed 0.9 on a file that should be 0? The miss is +0.9 — a big correction.
  • The nudge is scaled by the feature. A feature that was 0 for this file gets no blame at all. Only what was actually present moves.
  • Learning rate lr = 0.3 is the step size. Too big and it overshoots forever; too small and it never arrives.
  • L2 1e-3 gently shrinks every weight toward zero each step, so no single feature is allowed to become a dictator. This is how the model is stopped from memorising its training set.
def fit(self, samples, *, epochs=400, lr=0.3, l2=1e-3):
    # every weight starts at zero: no opinions yet
    for f in FEATURES: self.weights.setdefault(f, 0.0)
    n = len(samples)

    for _ in range(epochs):
        grad  = {f: 0.0 for f in FEATURES}
        gbias = 0.0

        # 1 · how wrong were we, on every example?
        for feats, label in samples:
            err = self.predict_proba(feats) - label
            for f in FEATURES:
                grad[f] += err * feats.get(f, 0.0)
            gbias += err

        # 2 · nudge, and shrink (L2) so nothing runs away
        for f in FEATURES:
            self.weights[f] -= lr * (grad[f]/n + l2*self.weights[f])
        self.bias -= lr * (gbias/n)

    self.trained_on = n
    return self

Full-batch gradient descent, no minibatching, no momentum, no Adam. Small data and a seventeen-weight model — nothing fancier earns its complexity here.

11 · Step 4 of 4 — labels

Where do the right answers come from? Weak supervision.

To learn, the model needs examples where somebody already knows the answer. Nobody is going to hand-label ten thousand files. So Testra writes a rough answer key — cheap, imperfect, and honest about being imperfect.

weak_label() says 1 when a file is UI-facing and carries something a test could hold on to; 0 for configs, styles, assets, existing tests, and anything with no interactive surface at all.

This is deliberately called weak. It is a prior to bootstrap from — designed to be replaced. Once the self-heal loop and the benchmark harness have run, the labels can be re-fit on real signal: which files actually produced verified, low-fragility selectors.

def weak_label(path, content) -> int:
    f = extract_features(path, content)

    # never a test target
    if f["is_config"] or f["is_style_or_asset"] \
                       or f["is_test_file"]:
        return 0

    interactive = (f["n_forms"] + f["n_buttons"]
                 + f["n_inputs"] + f["n_testids"]
                 + f["has_onclick"])

    ui_facing = (f["is_router"] or f["in_pages_dir"]
              or f["in_components_dir"]
              or f["has_auth_keyword"])

    return 1 if (ui_facing and interactive > 0) else 0
12 · Shipping the model

Readable weights, and a model that is allowed to be absent.

Training writes a plain JSON file — importance_model.json — that any human can open and argue with. There is no pickle, no .h5, no vendor format.

{
  "weights": { "n_testids": 2.41,
               "is_config": -1.87, ... },
  "bias": -0.42,
  "trained_on": 8412,
  "features": [ ...17 names, in order... ]
}

And here is the safest part: if that file isn't there, nothing breaks. Testra just goes back to the old ladder of rules. The clever thing is allowed to be missing.

# loaded once at import — None if no artifact
_ACTIVE = ImportanceModel.load()

def learned_score(path, content, fallback):
    m = _ACTIVE
    return (m.score_1_to_10(path, content)
            if m is not None else fallback)
Cost

Loaded once

Module-level, so the extractor pays the load cost a single time — not once per file.

Safety

Try/except on load

A corrupt artifact returns None, which means "use the heuristic", not "crash the request".

Covered by tests/test_importance_model.py: feature extraction, sigmoid bounds, that fit actually separates positives from negatives, JSON round-trips, and that a missing artifact falls back cleanly.

13 · The second model

Fragility: which selectors will break next month?

Validation catches selectors that are wrong today. This catches the ones that are right today and brittle tomorrow. It is a linear weighted scorer — the same shape as logistic regression, but with weights set by hand from the well-known locator hierarchy rather than fit by gradient descent. The weights are stored as data, so the benchmark harness can re-fit them from real break data later.

A good handle is one that won't move. "The button labelled Log in" survives a redesign. "The third box inside the second box" does not.

Every selector gets a risk score 0.0 → 1.0, a grade, and a reason attached. The suite gets one letter from the mean.

A < 0.25B < 0.40 C < 0.55D < 0.70F ≥ 0.70
Why not an LLM

Shape, not meaning

Brittleness is a small, stable function of a selector's shape. A linear scorer does that cheaply, deterministically, with a reason per score — and zero token cost.

Honest naming

Risk, not probability

It is called a risk estimate because that is what it is. It is never dressed up as a measured probability.

15 · The agents

Two AI agents, each with exactly one job.

Agent 1 · agents/filter_agent.py

The reader

Runs the extractor, then asks the LLM — in strict JSON mode — for a structured reading of the project: a summary, the key pages, the routes, and the testing challenges it can foresee.

Output is a FilterResult, serialized into SQLite so the job survives a server restart.

Agent 2 · agents/writer_agent.py

The writer

Builds a grounding list of real selectors pulled from the actual source, injects it into the prompt, plans the file list, then generates each file in its own call so a large suite can't be truncated mid-way. Finally it validates every selector it wrote and flags anything it can't find.

The model writes page objects and specs — nothing else. Everything that makes them runnable comes from the scaffold; everything that makes them trustworthy comes from grounding.

One agent reads the school and draws the map. The other walks the map and writes the checklist. Splitting them means neither has to be brilliant at both.

16 · The trust pipeline

Grounding: prove every selector points at something real.

This is the failure the product exists to prevent — a suite that looks perfect and dies on the first run because the model invented a button. Four components attack it, and none of them execute the generated code. They reason about it statically.

Evidence A

Source grounding

Extracts every anchor that genuinely exists in your repo — ids, test-ids, classes, form names, ARIA roles, accessible labels, link and button text — each carrying provenance: the file and line it was declared on. The UI cites LoginForm.tsx:42 instead of asking you to trust it.

Evidence B

DOM grounding

If you give a live URL you own, the deployed page's real HTML is fetched through the security scanner's SSRF-guarded, non-executing path. Stronger evidence, because it is literally what the browser will see.

Repair

The self-heal loop

Selectors that missed are fed back to the model together with the real anchors that do exist — so the fix is a grounded substitution, not another guess.

Shape

Static validation

Python compiled with py_compile, JavaScript checked with node --check, TypeScript structurally verified for balanced brackets and non-truncation.

The rule of the whole project: never claim more than you measured. Testra says "this selector provably resolves" — it never says "these tests will pass", because it never ran them.

  • Fragility grade distribution — so a suite can't score well by grounding everything to nth-child.

19 · Runnable, not just written

The scaffold: everything the LLM shouldn't be asked to guess.

Dependency manifests, framework config, GitHub Actions and GitLab CI, and the README are templated, not generated — there is exactly one correct answer per framework, and asking a model for it only introduces variance.

This module exists because the alternative failed silently for every single user: the CI template ran npm ci while nothing ever emitted a package.json. The pipeline could not pass on any repo, and neither half knew about the other. The install step and the manifest it installs are now written by the same module.

Invariant 1

The suite owns e2e/

Never the repo root. A React app already has a package.json there; writing ours over it would destroy the manifest of the app under test.

Invariant 2

BASE_URL wins, then a local webServer

One variable points the same suite at staging or prod. Unset, the config boots the app — so a fresh clone and CI both work with no arguments.

The AI writes the clever part. The templates write the boring part. That's why the pipeline is green the first time you run it.

20 · Beyond tests

Security scanning, publishing, accounts, admin.

services/security_scanner.py · 1,187 lines

Passive production scan

Point it at a URL you own and it audits configuration: HTTPS + HSTS, CSP, X-Frame-Options, cookie flags, CORS misconfiguration, version disclosure, mixed content, and a short curated list of files that should never be public (.env, .git/config). It sends no attack payloads and brute-forces nothing.

services/zap_scanner.py

Active scanning, opt-in

docker compose --profile zap up starts an OWASP ZAP daemon. Without it, scans degrade to the passive audit and say so — /api/scan/capabilities reports whether it's ready and why not.

SSRF guard

Refuses to be a weapon

localhost, private ranges and link-local addresses are blocked — including across redirect hops. A scope gate blocks third-party sites the user plainly does not own.

services/git_publisher.py

Publish to GitHub

Sign in with GitHub — no Personal Access Token to paste — and Testra creates the repo and pushes the suite. Tokens are encrypted at rest.

auth · billing · quota

Real accounts

Email + password with verification and OTP, Google OAuth, GitHub OAuth, session revocation, monthly generation quota, Free and Pro plans with a Stripe webhook.

services/admin.py

The one privileged role

Admins live in an ADMIN_EMAILS config allowlist, not a users.role column — so there is no row to write to escalate and no promote endpoint to abuse. Non-admins get 404, not 403: a 403 would confirm the console exists.

21 · Honesty

What Testra does not claim.

The project ships a model card. "Validated" means the file passed a static syntax check — nothing more. It does not mean the tests were executed, that the selectors resolve against your running app, or that the assertions pass.

Known limit

Regex-based extraction

Anchor extraction can miss dynamic classes (className={styles.x}) and CSS-in-JS, so both false positives and false negatives are possible. AST-based extraction is on the roadmap.

Known limit

Very large repos

Low-priority files are summarized rather than sent verbatim, which can reduce selector accuracy. Retrieval-based context selection is on the roadmap.

Known limit

Output ceilings

Extremely large suites can hit provider output-token limits. Narrow the scope and regenerate.

Known limit

Run-to-run variance

Quality depends on whichever free provider was available. The provenance report always says which model actually answered.

Saying "I checked this much, and no further" is not a weakness in the project. It is the feature that makes the rest of it believable.
