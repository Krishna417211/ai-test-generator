Every selector, traced back to the line it came from.

Testra reads your web application and writes a runnable Playwright, Cypress or Selenium suite. Then it does the part most tools skip: it proves where each selector came from, and states plainly what it did not check.

Read the source How it works
Two ways in

Point it at a running site, or hand it the source.

Crawl-first

Written from the live DOM

Give it your repository URL and your deployed URL. It renders and crawls the real application and writes tests from the elements a browser actually builds. Your file contents never reach the model — the repository is touched only to confirm access and name the stack.

Source-first

Written from the code

Upload the project, or run the CLI inside it. Testra filters it, generates a validated suite with a working CI pipeline, and pushes the whole thing to a brand-new repository in a single commit — then reads it back to confirm every file arrived.

01–05Method

The pipeline, in order.

The numbering is real: each step consumes the one before it, and a failure at any point stops the rest rather than being papered over.

01

Filter, before a token is spent

A deterministic pass keeps only what renders in a browser, scores each file for testing value, and fits the winners into a budget. No model runs until there is something worth showing one.

02

Read the project

One agent builds a structured account of the application — its routes, its key screens, the obstacles a test will hit — grounded strictly in files that exist.

03

Write the suite

A second agent writes Page Object classes and specs, using selectors extracted from your real markup rather than invented ones. Configs, CI pipelines and the README are templated, never generated — each has exactly one right answer, so asking a model only adds variance.

04

Ground, then repair

Every id, test-id and class is checked back against your source or your rendered page, carrying the file and line it was declared on. Misses go back to the model together with the anchors that really do exist — a grounded substitution, not a second guess.

05

Publish, and verify it landed

The suite is pushed to a new repository, and the commit tree is read back to confirm every file is present with the exact content that was uploaded. Anything missing is pushed again; anything still missing fails loudly.

Refusals

The things it will not do with your code.

Handing a tool your repository is an act of trust. These are the places where the answer is a flat no, enforced in code rather than promised in a policy.

Credentials are never sent

.env, SSH keys, PEM files, cloud service-account JSONs and hard-coded API tokens are detected and held back — from the model prompt and from the push. Every withheld file is named, never silently dropped. Run the CLI and the scan happens before anything leaves your machine at all.

Nothing is written over your files

Generated paths are sanitised — no traversal, no absolute paths, nothing inside .git — and merged without overwriting anything already in your project. A collision keeps your version and says so.

“18 files pushed” is checked

Every write in a push can return success and still leave the branch short. The commit tree is read back and compared by content hash, so the count is a statement about your repository rather than about our bookkeeping.

Sessions can't be read out of a backup

Session tokens are stored as hashes, so a leaked database, snapshot or support copy yields nothing that can be presented as a login. Logins are throttled per account, not just per address — the shape a real credential-stuffing run takes.

Terminal

Or run it where the code already is.

The web page can only be handed an archive somebody assembled by hand. The CLI runs inside the project, so your own .gitignore decides what is uploaded and credentials are caught before they are transmitted. Zero dependencies — Node's standard library only.

Signing in shows a short code you approve in a browser — on any device, including your phone. Your password never passes through the terminal.

Honestly

What it can't do yet.

It doesn't run the tests. Executing a suite needs a container and a live target, so every number here describes the generation, not the outcome. This is the next thing being built, and until it exists the scoring stays deliberately modest.

A crawl can't reach everything. It follows links and application routes; it does not drive your interface. A modal or a wizard step that only opens on click is never visited, so its selectors are never grounded.

Selector extraction is pattern-based. It can miss classes computed at runtime and some ARIA and text selectors, which is why an untraced selector is flagged for review rather than reported as broken.
