Project Report

Testra

An AI system that reads a web codebase and writes a grounded, runnable end-to-end test suite — with two LLM agents, a from-scratch logistic-regression classifier, and a selector-durability model.

Author krishnapriya Date 28 July 2026 Backend ~20,000 LOC Python Tests 1050 Licence MIT
How to read this report Every section opens with the technical account, and where a concept is genuinely hard, an italic plain-language paragraph restates it with no jargon at all. Those paragraphs are marked In plain words and are written so a curious child could follow them. Nothing in them is dumbed down to the point of being wrong.

01Abstract

Testra is a full-stack web application that converts a source repository into a complete, ready-to-run end-to-end (E2E) test suite. A user supplies a GitHub URL or a ZIP archive; Testra filters the repository down to browser-facing files, has one LLM agent build a structured reading of the project, has a second LLM agent write Page Object Model classes and specification files grounded in selectors extracted from the real source, verifies every selector it produced, repairs the ones that failed, grades the suite for long-term durability, scores the run against the checks it can actually perform, and delivers the result as a downloadable archive or a freshly published GitHub repository with working CI. A zero-dependency command-line client publishes the same way from inside the project, where the project's own ignore rules apply and credentials can be caught before anything is transmitted.

Two machine-learning components sit inside that pipeline. The first is a logistic-regression classifier implemented from scratch — no numpy, no scikit-learn — that learns which files in a given codebase are actually worth testing. The second is a linear weighted scorer that predicts how likely each generated selector is to break as the application evolves. Both are deliberately small, fully inspectable, and serialized to human-readable JSON.

The organising principle of the project is evidential honesty: the system never asserts a property it did not measure. It reports that a selector provably resolves to a real element; it never claims the test will pass, because it never executes the suite.

02The problem

End-to-end testing is the practice of driving a real browser through a real application the way a real person would: open the page, click the login button, type a password, confirm the dashboard appears. It is the only form of testing that verifies the product as the user experiences it, and it is the first thing teams abandon, for four reasons.

Cost

It is slow to write

A mid-sized application needs days of specialist work, repeated every time the interface changes.

Skill

It is easy to write badly

Good suites need Page Object Models, stable locators, environment configuration and CI wiring — not just a sequence of clicks.

Hallucination

Naïve AI makes it worse

Ask a general chatbot for a test suite and it will confidently produce #submit-button for a button that does not exist. The suite looks complete and fails on the first run.

Decay

Locators rot

div > div:nth-child(3) > button is correct today and broken the moment a developer adds a wrapper element. The suite starts failing for reasons unrelated to the product.

In plain wordsImagine a huge toy shop. Every morning, someone has to check that every door opens, every button beeps and every price tag is right. Doing it by hand takes hours, so people stop doing it — and one tired morning, the broken door goes unnoticed. Testra builds the little robot that does the checking, and then shows you exactly which doors it really checked.

03Objectives

  1. Zero-friction input. A public GitHub URL, a private repository via GitHub sign-in, or a dragged ZIP — nothing to install, no configuration file to write.
  2. Multi-framework, multi-language output. Playwright, Cypress and Selenium across TypeScript, JavaScript, Python and Java.
  3. Grounded generation. Every selector the model emits must be traceable to a real anchor in the source, or explicitly flagged as unverified.
  4. Runnable on arrival. The delivered suite must include its dependency manifest, framework configuration and CI pipeline, and must pass its own install step without editing.
  5. Durability awareness. The suite must be graded on how well it will survive future UI change, not only on whether it is correct today.
  6. Learned file selection. File importance must adapt to the codebase in front of it, rather than relying permanently on frozen path heuristics.
  7. Operational resilience. No single LLM provider outage or rate limit may take the product down.
  8. Measurable, honest quality. Report the metric the system can actually prove, with correct denominators.

04System architecture

Testra is a two-tier application: a React single-page frontend and a single FastAPI backend service, with SQLite for durable state. There is no message broker and no worker fleet; long operations stream their own progress over the request that started them.

The working flows

There are two pipelines, and they differ in what the suite is written from. That distinction matters more than any other design decision in the system, so it is worth stating before the step lists.

Generate · crawl-first

Written from the live site

The user supplies a GitHub URL and a hosted URL. Testra renders and crawls the deployed application and writes tests from its real, rendered DOM. Repository file contents are never sent to the model at all — the repo is touched only to confirm access, name the stack, and later publish the suite back.

Publish · source-first

Written from the source

The project is filtered, a validated suite is optionally generated from its source files and folded in, and the whole thing is pushed to a brand-new GitHub repository in a single commit.

The publish pipeline has two front doors. The browser takes a ZIP the user assembled by hand; the command-line client (§19) runs inside the project instead, so the project's own .gitignore decides what is uploaded and credentials are detected before anything is transmitted rather than after it arrives. Both reach the same /api/publish-zip and the same pipeline below — only the way the files are gathered differs, and that difference is the whole reason the CLI exists.

Flow 1 — generate (crawl-first)

  1. POST /api/analyze-crawl — render and crawl the hosted site (services/live_crawler.py), merging every reachable route's anchors into one index. The crawl is first because everything downstream depends on it, so its failure short-circuits before anything is spent on the repo. There is deliberately no repo-file fallback: a suite silently written from source when the user asked for a live crawl is not the thing they asked for. A site that renders but exposes too little markup is refused with a reason rather than grounded against near-nothing.
  2. Repo touch — confirm access via the GitHub API and fetch only the manifest files (package.json, requirements.txt, Gemfile…) needed to name the stack. The job, including the crawl anchors, is persisted to SQLite.
  3. GET /api/stream/{job_id} — Server-Sent Events push Agent 2's output token by token. The raw output is cached on the job so the generate call can reuse it, avoiding a second paid LLM call.
  4. POST /api/generate/{job_id} — reserve a generation credit, run Agent 2 against the crawl index (or reuse the streamed output), then: sanitize every model-authored filename, place the suite under e2e/, ground each selector against the crawl anchors, self-heal both syntax failures and unverified selectors, add the templated scaffold and CI, validate the whole set, grade fragility, and compute the success rate. The credit is refunded on any failure; the job — and the user's source with it — is deleted immediately afterwards.

Flow 2 — publish (source-first)

  1. Read — the ZIP is decoded in memory with a zip-slip guard on every path.
  2. Filter — filter_for_push drops credentials first, then dependency and build junk, binary assets, oversized files, and any path that cannot be safely written. Withheld credential files are named in the response, not merely counted.
  3. Suite (when CI is requested) — Agent 1 reads the project, Agent 2 writes the suite with the self-heal loop running until it is green before the push, so what lands in git is already validated and we push exactly once. Nothing here can cost the user their push: a project with no testable UI, or a provider outage, skips this step with an explicit warning and the code still lands.
  4. Merge — generated files are added without ever overwriting one of the user's own; a collision keeps their version and says so.
  5. Push — blobs → tree → commit → ref via the GitHub Git Data API, no local git binary, one commit.
  6. Verify — the pushed tree is read back and every expected path is confirmed present with the exact content hash uploaded. Missing files are re-pushed once; anything still missing fails the publish outright.
  7. Record — the repository is remembered so the dashboard can show it and the user can undo the whole thing with one click.

Both flows report their steps as NDJSON over the request that started them (services/progress.py), which is why a two-minute operation shows real progress without a message broker or a worker fleet. Anything decidable before the stream opens — a malformed URL, a missing repo name, a corrupt archive — stays a plain HTTP error, because an in-band error on a 200 response is harder for every client to handle.

06Stage 1 — the deterministic extractor

services/file_extractor.py (658 lines) performs all the work that does not need a language model, before a single token is spent. It filters a raw {path: content} dictionary down to browser-facing UI files, detects the technology stack, scores every survivor for importance, and fits the winners into a token budget.

Stack detection

React, Vue, Next, Nuxt, Angular and Svelte on the frontend; Django, Flask, FastAPI, Rails and Laravel plus their template engines on the server side. Detection drives both the prompt and the scaffold that will be generated later.

Importance scoring — the hand-written ladder

9pages/ app/ views/ screens/Whole screens a user lands on
8Layouts; auth, login, signup, form, checkout, cartHighest-value flows in almost every product

Token budgeting

The extractor targets a 600,000-token budget. Files are added in descending importance until the budget is reached. Crucially, files that do not fit are summarized rather than dropped: their ids, classes and routes are extracted into a compact stand-in, so the model still receives the anchors it needs to write real selectors even for files it never sees in full. A warning surfaces in the UI when this happens.

In plain wordsA big project is like a whole school. Testra only cares about the rooms children actually walk into — not the boiler room and not the store cupboard. So it walks the corridors first, marks the doors worth checking, and if there are too many doors to describe in full, it writes a short note about the far ones instead of forgetting them.

07The logistic-regression model

services/importance_model.py (226 lines) is the project's principal machine-learning component: a binary logistic-regression classifier written from first principles, with no numerical or ML dependency of any kind.

7.1 Why a learned model at all

The ladder in section 06 encodes good priors, but they are permanently frozen and they look only at the path. It cannot notice that in a particular codebase the pages/ directory holds thin two-line shells while every interactive control lives in features/. The consequence is concrete and costly:

Rule sees only the name

pages/About.tsx → 9

Forty words of static text, nothing clickable, nothing a test could assert — yet ranked at 9 and sent to the model at full length, consuming budget.

Body tells the truth

features/Checkout.tsx → 6

Three forms, nine inputs, a data-testid on every control. The single most testable file in the repository, ranked below the About page.

The learned model refines the score using the file's body, so it can rank on evidence rather than on directory convention.

7.2 Why logistic regression specifically

  1. The question is binary. "Would a UI test ever target this file?" is a yes/no with a useful confidence attached — precisely the shape logistic regression fits.
  2. The data is thin and the features are few. Seventeen features and a few thousand rows do not justify a neural network; a higher-capacity model would overfit and explain nothing.
  3. Interpretability is a product requirement. Every coefficient is a named number attached to a named feature. When a file scores 9, the reason is legible.
  4. It costs nothing to run. One multiply-add per feature. No GPU, no service call, no latency to the request path.

7.3 Step one — feature extraction

extract_features(path, content) converts each file into exactly seventeen numbers in the range 0 to 1. Binary features are 1 or 0; count features are divided by a saturation constant and clipped, so one enormous file cannot dominate the sum. Extraction is regex-only: no parsing, no LLM, microseconds per file.

Design constraintThe FEATURES list is the model's contract — the weight vector is aligned to its order. Adding, removing or reordering a feature invalidates every saved weight, so the list is treated as a versioned interface and changing it requires retraining.

7.4 Step two — the hypothesis

The model computes a linear combination of features, then passes it through the logistic (sigmoid) function:

# z = w·x + b        σ(z) = 1 / (1 + e^-z)

def predict_proba(self, features: dict[str, float]) -> float:
    z = self.bias + sum(
        self.weights.get(f, 0.0) * features.get(f, 0.0)
        for f in FEATURES
    )
    return 1.0 / (1.0 + math.exp(-z))

def score_1_to_10(self, path, content="") -> int:
    p = self.predict_proba(extract_features(path, content))
    return max(1, min(10, round(1 + p * 9)))

The sigmoid maps any real number onto the open interval (0, 1): strongly negative totals approach 0, strongly positive totals approach 1, and z = 0 gives exactly 0.5 — perfect indecision. The output is then mapped onto the 1–10 scale the rest of the application already speaks, so the learned score is a drop-in replacement for the heuristic score. A probability of 0.92 becomes a 9; 0.06 becomes a 2.

In plain wordsThink of a scorecard for picking a football team. "Can they run fast?" — add 3 points. "Can they kick?" — add 4. "Do they get tired quickly?" — take 2 away. Add it all up. Logistic regression is exactly that scorecard, with one extra trick at the end: it squashes the total onto a line from 0 to 1, so instead of a strange number like 7.4 you get something that reads as confidence — 0.9 means "almost certainly yes", 0.1 means "almost certainly no". And the points on the card are not chosen by a person; the machine works them out itself.

7.5 Step three — training by gradient descent

fit() is full-batch gradient descent on the cross-entropy objective with L2 regularization. All weights initialise to zero — the model begins with no opinions.

def fit(self, samples, *, epochs=400, lr=0.3, l2=1e-3):
    if not samples: return self
    for f in FEATURES:
        self.weights.setdefault(f, 0.0)
    n = len(samples)

    for _ in range(epochs):
        grad  = {f: 0.0 for f in FEATURES}
        gbias = 0.0

        # accumulate the gradient over every example
        for feats, label in samples:
            pred = self.predict_proba(feats)
            err  = pred - label                # how wrong, and which way
            for f in FEATURES:
                grad[f] += err * feats.get(f, 0.0)
            gbias += err

        # descend, with L2 shrinkage folded into the same step
        for f in FEATURES:
            self.weights[f] -= lr * (grad[f] / n + l2 * self.weights[f])
        self.bias -= lr * (gbias / n)

    self.trained_on = n
    return self
err = pred − label

The size and direction of the miss

Predicting 0.8 on a true positive gives −0.2 — a gentle nudge. Predicting 0.9 on a true negative gives +0.9 — a large correction. The gradient scales naturally with confidence in the wrong answer.

err × feature

Blame lands only where evidence was

A feature that was 0 for this example contributes nothing to its own gradient. Only features that were actually present move.

lr = 0.3

Step size

Too large and the weights oscillate past the minimum; too small and 400 epochs are not enough to reach it. 0.3 with normalised features is a stable middle.

l2 = 1e-3

Regularization

Every weight is shrunk slightly toward zero on each step, so no single feature can dominate on the strength of a coincidence in the training set. This is the model's defence against overfitting.

Deliberate simplicityNo minibatching, no momentum, no adaptive optimiser, no learning-rate schedule. With seventeen weights and a few thousand rows, none of that machinery would improve the result enough to justify the code that implements it.

In plain wordsIt is the game "warmer, colder". The machine starts knowing nothing. It guesses. We tell it how wrong it was. It shifts every point on its scorecard a tiny step in the direction that would have been less wrong. Then it does that again, four hundred times — and by the end, the scorecard is good.

7.6 Step four — where the labels come from

Supervised learning needs known answers, and nobody is going to hand-label thousands of files. Testra therefore uses weak supervision: a cheap, imperfect, explicitly-labelled-as-imperfect answer key.

def weak_label(path: str, content: str) -> int:
    f = extract_features(path, content)

    # categorically never a test target
    if f["is_config"] or f["is_style_or_asset"] or f["is_test_file"]:
        return 0

    interactive = (f["n_forms"] + f["n_buttons"] + f["n_inputs"]
                 + f["n_testids"] + f["has_onclick"])

    ui_facing   = (f["is_router"] or f["in_pages_dir"]
                or f["in_components_dir"] or f["has_auth_keyword"])

    return 1 if (ui_facing and interactive > 0) else 0

A file is labelled positive when it is UI-facing and carries something a test could anchor to. It is negative for configuration, styles, assets, existing tests, and anything with no interactive surface. This is the cold-start prior. The design intent — stated in the module docstring — is that the same fit() is re-run later on real signal: which files actually produced verified, low-fragility selectors, as measured by the grounding pipeline and the benchmark harness. The label function is scaffolding for the first model, not the permanent definition of truth.

7.7 Persistence and graceful degradation

Training writes importance_model.json — weights, bias, sample count and the ordered feature list — in plain, readable JSON. There is no pickle and no vendor binary format; a reviewer can open the artifact and disagree with a coefficient.

{
  "weights":    { "n_testids": 2.41, "is_config": -1.87, ... },
  "bias":       -0.42,
  "trained_on": 8412,
  "features":   [ "is_router", "in_pages_dir", ... ]
}

The most important property of the whole module is that it is allowed to be absent:

# loaded once at import; None when no artifact exists on disk
_ACTIVE: Optional[ImportanceModel] = ImportanceModel.load()

def learned_score(path, content, fallback: int) -> int:
    """Model score when a model is trained; the caller's heuristic otherwise."""
    m = _ACTIVE
    return m.score_1_to_10(path, content) if m is not None else fallback
No artifact

Silent fallback

Callers use the heuristic ladder. Importing the module changes nothing until a model is trained.

Corrupt artifact

Also fallback

load() catches every exception and returns None — a bad file means "use the heuristic", never "fail the request".

Cost

Loaded once

Module-level, so the extractor pays the deserialisation cost a single time rather than once per file.

In plain wordsThe clever part is allowed to be missing. If the learned scorecard isn't there, or is damaged, Testra quietly goes back to the older, simpler list of rules and carries on. Nothing breaks. That is what makes it safe to be clever in the first place.

7.8 What is tested

tests/test_importance_model.py covers feature extraction on representative files, sigmoid output bounds, that fit() actually separates positives from negatives after training, JSON round-tripping through to_dict/from_dict, and that a missing artifact degrades to the fallback path.

08The fragility model

services/fragility.py (262 lines) answers a different question: not "is this selector correct today" — grounding settles that — but "will this selector still work in three months". It is a linear weighted scorer over named features of the selector's shape.

Why not an LLM

Brittleness is a small, stable, explainable function of shape: does the locator lean on position, on depth, on a build-generated class, or on a stable contract like data-testid or an ARIA role? A linear scorer answers that deterministically, at zero token cost, with a human-readable reason attached to every score. The weights are stored as data (FEATURE_WEIGHTS), not logic, so the benchmark harness can re-fit them from real break data without touching the scoring code.

FeatureWeightWhat it detects

deep_chain+0.45Four or more combinators — couples the test to layout depth

The bias is 0.35: a featureless selector sits at medium risk, not zero risk, because the absence of evidence for durability is not evidence of durability. Each selector receives a risk score in [0, 1], a grade, the list of reasons that produced it, and — where one can be named — a sturdier suggested replacement. The suite receives a single letter from the mean.

A < 0.25B < 0.40C < 0.55D < 0.70F ≥ 0.70
Naming disciplineThe output is called a risk estimate, because that is what it is. It is never presented as a measured probability of failure, since no failures were observed to measure.

In plain wordsA good handle is one that won't move. "The button labelled Log in" will still be there after a redesign. "The third box inside the second box" will not. This model looks at how each instruction was written and warns you when it depends on something likely to shift.

10The two agents

Agent 1 — agents/filter_agent.py

Runs the extractor, then asks the LLM in strict JSON mode for a structured reading of the project: a summary, the key pages, the routes, and the testing challenges it foresees. The result is a typed FilterResult, serialized transparently into SQLite so the job survives a server restart.

Agent 2 — agents/writer_agent.py

  1. Build a grounding list of real selectors — ids, data-testid/data-cy, name attributes, classes — extracted from the actual source, and inject it into the prompt.
  2. Plan the file list for the suite.
  3. Generate each file in its own call, so a large suite cannot be truncated by a single output-token ceiling.
  4. Validate every selector produced against the source, and flag suspected hallucinations with a visible ⚠️.
  5. Optionally self-heal: re-prompt with the misses and the real anchors.
Separation of concernsThe model writes page objects and specs — nothing else. Everything that makes the suite runnable comes from the scaffold (section 12); everything that makes it trustworthy comes from the grounding pipeline (section 11).

In plain wordsOne helper reads the school and draws the map. The other walks the map and writes the checklist. Splitting the job in two means neither has to be brilliant at both.

11Grounding, self-heal and the success rate

The failure mode this product exists to prevent is a suite that looks perfect and breaks on its first run because the model invented a selector. Four components attack that, and none of them execute the generated code — they reason about it statically.

services/grounding.py

Source grounding

Extracts anchors that genuinely exist — ids, test-ids, classes, form names, ARIA roles, accessible labels, link and button text — each carrying provenance: the file and line it was declared on. The UI can therefore cite LoginForm.tsx:42 rather than ask for trust. Works for any repository.

services/grounding.py

DOM grounding

When the user supplies a live URL they own, the deployed page's real HTML is fetched through the security scanner's SSRF-guarded, non-executing path. This is the stronger evidence, because it is exactly what the browser will see.

writer_agent

The self-heal loop

Consumes the unverified set and re-prompts the model with the precise selectors that missed and the real anchors that exist — so the correction is a grounded substitution, not a second guess.

services/validator.py

Static validation

Python is compiled with py_compile; JavaScript is checked with node --check where Node is available; TypeScript and other files get structural checks for balanced brackets and non-truncation.

Both grounding modes are constructed identically — extract an anchor set, then perform a membership test — so a selector verified against source and one verified against the live DOM are judged by the same rules. No CSS engine is required: the selectors emitted reduce to a handful of anchor kinds, and membership is the question "would querySelector find this".

Honest accountingFileValidation records whether anything was actually verified, or whether there was simply no toolchain for that file type. Configuration and documentation files pass by default, so counting them as passes would inflate the number: "8/8 files passed syntax validation" reads as eight checked files when two of them were a README and a YAML nobody parsed. Callers reporting a rate count only genuinely checked files.

The generation success rate — services/success_rate.py

The measurements above are individually meaningful but collectively hard to read: a user looking at four fractions cannot tell whether the run went well. success_rate.py aggregates them into a single 0–100 figure with a letter grade, from four components:

ComponentWeightWhat it measures
Completeness0.35Planned files that were actually written. A suite missing a page object cannot run at all.
Parse0.30Code files that a real parser read successfully. Config and docs are excluded by checked=False.
Grounding0.25Selectors traceable to the user's real source or live DOM.
Coverage0.10Binary: did the suite end up containing runnable test cases at all?

The weights are deliberately unequal, and reflect how load-bearing each failure is rather than how easy it is to measure. A component with nothing to measure — no selectors, no parseable files — is dropped and its weight redistributed over the rest, never scored as a free 100%. Crediting a check that never ran is the specific inflation this module exists to prevent, and it is the one a naive average would commit.

NamingIt is a generation success rate, and the payload says so in a field the UI cannot omit. Testra never executes the generated suite, so any number labelled "accuracy" or "pass rate" would be invented. The failure mode of inventing one is not a slightly wrong figure: the user trusts "94% accurate", runs the suite, watches it fail, and does not come back. The API therefore ships measures and not_measured alongside the score so the caveat travels with the number to every client.

In plain wordsThe score answers "how well did the robot do its homework?" — did it write everything it planned, is the code well-formed, do the buttons it mentions really exist. It does not answer "will the tests pass?", because nobody ran them yet, and the report says that out loud instead of hoping you assume it.

12Safety gates and failure handling

Two operations in this system send the user's files somewhere they can never be recalled from: an LLM prompt goes into a third-party provider's logs, and a git commit survives even a force-push in the reflog. A third — writing files into a repository — can destroy work that was already there. The components below exist because each of those is unrecoverable, so the correct place to be careful is before, not after.

Credential exclusion — services/secrets_guard.py

A .env in an uploaded ZIP is the normal case, not the exotic one: people archive their working tree. Two detectors run before anything leaves the process.

path rules

Files that are credentials

.env and its environment variants, id_rsa, .pem/.key/.p12/.jks, .npmrc, .netrc, terraform.tfstate, anything under .aws/, .ssh/, .gnupg/, and cloud service-account JSONs. Template variants (.env.example) are deliberately kept — they are documentation and contain placeholders by definition.

content rules

Keys hard-coded in source

Only issuer-prefixed tokens — AKIA…, ghp_…, sk_live_…, AIza…, xox… — PEM private-key blocks, and database URLs with inline passwords. Generic api_key = "…" assignments are pointedly not matched: they are overwhelmingly placeholders, and a guard that eats half a codebase is a guard that gets switched off.

Exclusions are reported and named, never silent. A user whose .env quietly disappeared from a push will deploy, hit a missing-configuration error, and spend an afternoon on a problem we caused — so the response carries the path and the reason for every withheld file, and the UI lists them.

A bug worth recordingThe first implementation normalised paths with path.lstrip("./"). lstrip strips characters, not a prefix, so ".env" became "env" and the single most important file the module exists to catch walked straight through. It was caught by a test written from the leak's point of view rather than the code's. The same defect existed independently in the writer agent's filename handling, where it silently erased ../ traversal instead of rejecting it.

Safe filenames — services/safe_paths.py

Every path in a generated suite comes out of an LLM's JSON, which makes it untrusted input that happens to look structured. sanitize() repairs what can be repaired and rejects the rest:

  • Traversal is rejected, not repaired. A path that asked to be outside the suite root has no correct home to be moved to, and guessing one is how you overwrite the user's src/. Prefixing with the suite directory is not containment — git normalises e2e/../../src/App.tsx straight back out.
  • Absolute paths are relativised, because /tests/login.spec.ts has an obvious intent that traversal does not.
  • Windows-hostile names are repaired — trailing dots and spaces (silently trimmed by Windows, so the repo has two names for one file), reserved device stems (con.ts cannot be created at all), and the characters Windows forbids.
  • .git/ is off limits. Writing there does not add a file; it corrupts the repository. .github/workflows/ is explicitly allowed — the CI pipeline legitimately lives there.
  • Duplicates are renamed, not overwritten. Two planned files with one name means last-write-wins loses a spec and still reports the full count. The rename splits at the first dot, so login.spec.ts becomes login-2.spec.ts and never login.spec-2.ts — .spec. is what the runner discovers on, and suffixing after it produces a file that exists, parses, validates, and is never collected.

The counterpart, merge_new_only(), adds generated files to the push set without ever overwriting an existing key. Collisions are rare — the suite has its own directory — but "rare" is the wrong bar when the file being destroyed is the one thing in the request we did not write. It happens on a re-publish, or a repo that already has an e2e/.

Push verification — services/git_publisher.py

"18 files pushed" is a claim about the repository, and until recently it was a claim about our own bookkeeping. Every write in the blobs → tree → commit → ref sequence can return 2xx and still leave the branch short a file. The user is told the count, finds sixteen, and usually finds out much later — when CI runs a suite missing a page object.

The publisher now reads the pushed tree back (GET /git/trees/{sha}?recursive=1) and compares it against what it uploaded. Git makes this cheap and strict at once: a tree entry's SHA is the hash of its content, so comparing SHAs verifies bytes, not just names. A path present with different content counts as missing, which is the honest reading.

  1. Anything missing is re-uploaded and committed again, layered onto the tree that is now live rather than the original base — otherwise repairing one file would delete the three that landed.
  2. The second verification compares against the SHAs the repair actually uploaded, not the first attempt's.
  3. Anything still missing raises. It is never a success with a footnote.
  4. When the check itself cannot complete — GitHub truncates trees beyond roughly 100k entries — nothing is claimed as verified and nothing is claimed as missing. An unread tree is not evidence of absence, and the response says which case it was.

Protecting the account itself

The gates above protect the user's code. Four more protect their account, and each was chosen because the obvious version of it is wrong.

services/store.py

Session tokens hashed at rest

The sessions table was keyed by the bearer token itself. Since that token is the credential, with no second factor behind it, any read-only glimpse of the database — a leaked backup, a volume snapshot, an injection anywhere, a support copy — was live takeover of every signed-in account simultaneously. The table now holds a SHA-256 digest. Plain, unsalted, no work factor: those defend guessable secrets, and the input is 32 bytes of token_urlsafe; a per-row salt would also destroy the primary-key lookup that makes session validation one indexed read per request. Done inside the store rather than at the call sites, so a new endpoint cannot store a raw token by forgetting a helper.

services/login_guard.py

Login throttled per account

A per-IP limiter cannot see the attack that matters: credential stuffing spread over hundreds of addresses, each under the cap, collectively trying thousands of passwords against one inbox. So the counter is keyed on the account. It delays and never disables — locking an account would hand anyone who knows an email address a denial-of-service button. Failures are counted for the address as typed whether or not it exists, or the throttle becomes the account-existence oracle the 401 message carefully refuses to be.

services/file_extractor.py

Decompression bombs

The endpoint capped the archive, which says nothing about what comes out of it: DEFLATE reaches roughly 1000:1, so a compliant 10 MB upload can expand to 10 GB — held in memory as str, taking the process down for every user. Three limits, because each alone has a hole: per-member size, per-member ratio above a floor, and a total. Header sizes are attacker-controlled, so the real defence is a running total of what actually came out.

main.py

Headers from the app, not only the proxy

Caddy stays the authority for the browser-facing site (§20). These cover the API reached directly — in development, by the CLI, by any deployment that publishes port 8000 without the proxy. Narrow and API-appropriate: nosniff, DENY, no-referrer, and a default-src 'none' policy. The interactive docs are excluded by path, since they load Swagger from a CDN and that policy would render them blank.

A migration that had to be losslessRows written before hashing held the token itself, and hashing them in place is precisely what a lookup now computes — so the migration invalidates nothing and nobody is logged out. It is guarded by PRAGMA user_version, and that has to be a guard rather than a heuristic: a second pass would hash the hashes and sign out every user at once, with no way back. The guard is set inside the same transaction as the rewrite, so a crash mid-migration rolls both back and the next start retries cleanly.

Unsupported projects and failed generation

Two failure classes are handled explicitly rather than being allowed to present as success.

filter_agent

Unsupported project

An empty upload, a documentation repository, an API-only backend and a monorepo whose frontend was filtered out are four different mistakes needing four different actions. A single "no testable UI found" cannot tell the user which they are in, so NoTestableUIError diagnoses the case, carries a machine-readable code, and the API returns it as a structured 422 the client can render as a real screen.

writer_agent

Total generation failure

When a response is not valid JSON, the parser falls back to a single file containing the raw output. That file used to be scaffolded, validated, zipped and handed over as e2e/tests/generated.ts — a plausible-looking archive containing the model's prose, which parses as nothing and collects no tests. It now raises GenerationFailedError: a failure that presents as success is the one outcome worth an exception.

A partial run is a third, softer case and is treated differently: the files that generated are kept, the missing ones are named in failed_files, and the CI workflow is withheld — because a pipeline that runs an incomplete suite is guaranteed red, and a red pipeline is worse than none.

In plain wordsThree promises. We never send your passwords anywhere. We never write a file on top of one of yours, or in a place you didn't ask for. And when we say we saved eighteen files to your account, we go and count them afterwards — and if one is missing we put it back, or we tell you we couldn't.

13The scaffold

agents/scaffold.py produces the dependency manifest, framework configuration, GitHub Actions and GitLab CI pipelines, and the README. These are templated, not generated: each has exactly one correct answer per framework, so asking a language model for them only introduces variance.

The module exists because the alternative failed silently for every user: the CI template ran npm ci while nothing ever emitted a package.json. The pipeline could not pass on any repository, and neither half of the system knew about the other. The install step and the manifest it installs are now written by the same module.

Invariant 1

The suite owns e2e/, not the repo root

A React application already has a package.json at the root; writing ours over it would destroy the manifest of the application under test.

Invariant 2

BASE_URL wins, then a local webServer

One environment variable points the same suite at staging or production. Unset, the configuration boots the application, so a fresh clone and CI both work with no arguments. Base URLs are normalised to a trailing slash and tests navigate with slashless relative paths — the only combination under which a sub-path deployment such as a GitHub Pages project site stays addressable.

14The LLM router

services/llm_router.py (948 lines) is the availability layer. It tries providers in priority order, rotates round-robin through each provider's configured keys, and places a key on cooldown when it returns a 429 or errors. A json_mode flag forces valid JSON per provider, and per-request status updates are scoped with a ContextVar so concurrent streams never cross-talk.

In plain wordsIt's like having three friends who can help with your homework. Ask the first one. If they're busy, ask the second. If everyone's busy, wait a minute and try again — and always say honestly which friend actually answered.

15Persistence and live progress

services/store.py — the durable job store

1,157 lines of SQLite-backed state using only the standard library. Jobs survive process restarts and are shared across workers; old jobs are pruned by TTL (24 hours). FilterResult is serialized to and from JSON transparently, so callers deal in typed objects, not rows.

services/progress.py — NDJSON step streaming

The four long POST endpoints — /api/analyze, /api/upload-zip, /api/scan and /api/publish-zip — stream newline-delimited JSON: one {"type":"step"} line per phase as it starts and finishes, then a single result or error. The client lights up a flowchart from it, so a 10–60 second wait shows which phase is running and what it found.

NDJSON over the endpoint's own response body was chosen rather than SSE because all four are POSTs and two carry a multipart upload, while EventSource can only issue a GET with no headers and no body. Streaming in-band keeps the request's authentication header and its file attached.

The trade-off this forcesBecause the HTTP status line is sent before the work runs, a mid-flight failure cannot be an HTTP status. Errors therefore split by when they become decidable: anything pre-flight — a malformed URL, a missing token, a spent quota — is raised before the first byte and remains a real 400/403/402. Anything after is emitted in-band carrying its status, and the client re-raises the identical exception, so a 402 opens the upgrade modal either way.

Step ids are a cross-language contract with frontend/src/flows.ts. A drifted id would be silent in the browser — the card simply never lights — so Progress rejects an unknown id rather than emitting an event nothing listens for.

16Security scanning

Passive configuration audit — services/security_scanner.py

1,187 lines. Given a URL the user owns, it fetches the site and inspects its configuration for the issues that commonly bite web applications in production. It is deliberately non-intrusive: it reads headers, cookies, TLS and redirect behaviour, and probes a short curated list of files that should never be public. It sends no attack payloads and brute-forces nothing.

  • HTTPS enforcement and HSTS
  • Security headers — CSP, X-Frame-Options, X-Content-Type-Options, Referrer-Policy, Permissions-Policy
  • Cookie flags — Secure, HttpOnly, SameSite
  • Server and framework version disclosure
  • CORS misconfiguration — Access-Control-Allow-Origin: * together with credentials
  • Accidentally exposed sensitive files — .env, .git/config
  • Mixed content and insecure form actions

Active scanning — services/zap_scanner.py

Opt-in via docker compose --profile zap up, which starts an OWASP ZAP daemon alongside the stack. ZAP takes about a minute to become responsive; the backend waits for it rather than quietly falling back. Without the profile, active scans degrade to the passive audit and say so. GET /api/scan/capabilities reports whether active scanning is available, and why not if it is not.

The SSRF guard

Scans of localhost, private ranges and link-local addresses are refused — including across redirect hops, so a public URL cannot redirect the scanner into an internal network. A scope gate additionally blocks third-party sites the user plainly does not own. The same guarded, non-executing fetch path is reused for DOM grounding.

17Accounts, billing and administration

services/auth.py

Authentication

Email and password with verification and OTP, Google OAuth, GitHub OAuth, password reset, session revocation across all devices, and account deletion.

services/quota.py + billing.py

Plans and quota

Free plan with a monthly generation allowance; Pro with unlimited runs and a stronger model. limit_for() and tier_for() are deliberately adjacent — they are the only two things a plan changes.

services/git_publisher.py

Publishing

Sign in with GitHub — no Personal Access Token to paste — and Testra creates the repository and pushes the suite. Linked tokens are encrypted at rest when SESSION_SECRET is configured.

services/admin.py

The admin role

User management, plan and quota overrides, platform analytics, and provider/key health, behind require_admin on every /api/admin/* route.

Two deliberate security decisions

  1. The admin grant lives in ADMIN_EMAILS config, not a users.role column. With no row that confers privilege, there is nothing to write in order to escalate, no promote-user endpoint to abuse, and no path from a stolen session to a second administrator. The trade is that changing the admin list requires a config change and a restart — the right friction for the one role that can read every account. The address must also be verified: with REQUIRE_EMAIL_VERIFICATION=false, a stranger could sign up as an admin's address, so the allowlist alone is not proof of who holds it.
  2. Non-admins receive 404, not 403. A 403 confirms the console exists to anyone holding a session. To everyone else it should look absent. The client's user.is_admin flag decides only whether the navigation item renders; every route re-derives the role server-side.

19The command-line client

The web application can only ever be handed an archive somebody made by hand, and that is a real limit rather than an inconvenience. It cannot know which files the project considers its own, and it cannot inspect anything until the bytes have already crossed the network. cli/ is a small Node package (npx @testra/cli) that runs inside the project and closes both gaps.

What running in the project buys

cli/src/collect.js

The user's own ignore rules

Files come from git ls-files -co --exclude-standard — git's answer to "what belongs to this project", honouring nested .gitignores, .git/info/exclude and the global excludes file. The server must guess with a fixed skip-list that knows node_modules and dist but not .turbo, .astro, or whatever this year's build tool named its cache. The project's own ignore file already lists them.

cli/src/secrets.js

Credentials that never leave the machine

The scan of §12 runs before the upload rather than after it. On the web, the server is the earliest point at which a .env can be caught, and by then it has already been transmitted. Here it never is. The server re-scans regardless — defence in depth — so the layers fail safe in only one direction.

It also runs headlessly in CI with a token from a secret store, which the upload page cannot do at all.

Zero dependencies, and why that is load-bearing

The package declares no runtime dependencies and uses only Node's standard library. For a tool whose stated value is "your credentials never leave this machine", every transitive dependency is something a reviewer has to take on trust — so the ZIP encoder is written against node:zlib (roughly a hundred lines: CRC-32, local and central headers, EOCD) and the flag parser is node:util.

How a hand-rolled encoder is made defensibleNot by inspection. backend/tests/test_cli_zip.py builds archives with the CLI's encoder and extracts them with services.file_extractor.extract_zip() — the exact function /api/publish-zip calls — asserting the round-trip byte for byte, and Python's zipfile.testzip() independently verifies every CRC. Unicode paths, empty files, CRLF and a 600-entry archive are all covered. If the encoder is wrong, it fails against its real consumer rather than against a mock of one.

Signing in without a password — RFC 8628

A command-line tool cannot own a browser redirect: it may be running over SSH on a machine with no browser and no way to receive a loopback callback. The device authorization grant solves exactly this. The CLI requests a short code, the user approves that code in a browser anywhere — a phone is sufficient — and the CLI polls until the approval lands. The password never passes through the CLI at all.

Two codes are issued, and conflating them would be the security bug in this design:

device_codeuser_code
Shape43 random charactersABCD-EFGH
Held bythe CLI, never displayedthe human, read off one screen and typed into another
Is it secret?Yes — possession entitles the bearer to collect the session tokenNo — it is designed to be shown, and grants nothing on its own
Defenceentropy; returned exactly once, then destroyedneeds an authenticated browser session to approve; 10-minute life; hard submission cap

The signed-in browser session is the entire authorisation: the token the terminal receives belongs to whoever approved it. The user_code alone approves nothing, which is what makes it safe to display.

A rate limit on the wrong endpointThe intuitive move is to throttle the endpoint that mints codes. It is wrong twice: minting hands the caller a code they already know, so it buys an attacker nothing, and a strict per-IP cap there locks out an entire office behind one NAT address — these buckets are per-IP. The tight cap belongs on code submission, the only brute-force surface, where ten attempts per ten minutes puts a 6.6×1011 space many orders of magnitude out of reach within a code's lifetime. A test pins the reasoning so it is not "simplified" later.

The browser half (/cli) is written as a consent screen rather than a confirmation dialog, because it must be possible to arrive there having not started a login: a prefilled code is never auto-approved, Reject is a peer of Approve rather than a cancel link, and the page states what approving grants before granting it.

What the CLI cannot do

It publishes; it does not generate from a live crawl. That flow needs a headless browser driving the deployed site, which belongs on the server (§04). The CLI's scope is deliberately the one flow where running beside the source is an advantage.

In plain wordsThe website has to be handed a folder in a box. The terminal tool is already standing in the folder — so it can read the project's own list of what to ignore, and it can check for passwords before anything is posted rather than after it arrives. And signing in never involves typing your password into the terminal: it shows you a short code, you tap approve on your phone, and it carries on.

21Deployment

The whole system runs with one command: docker compose up — frontend on port 5173, API on 8000, interactive OpenAPI docs at /docs. Optional active scanning is a compose profile rather than a default dependency.

22Benchmarking

services/benchmark.py runs the grounding and fragility analysis over a set of (repository, generated suite) cases and prints a markdown leaderboard. It reports:

  • Verified-selector rate — of every selector the model wrote, the fraction that provably resolves to a real element in the source or the live DOM. Pooled and per-repository.
  • Fragility grade distribution — so a suite cannot score well by grounding everything to nth-child.

The harness is explicit about denominators: a case that grounded nothing counts as a case with no measurable rate, not a free 100%, and aggregates are computed only over cases that actually had selectors. It runs two ways — over pre-generated suites (fast, free, deterministic; used in CI to catch a regression in grounding itself), or over the full pipeline with real API keys to produce headline numbers.

Why this metricBecause Testra never executes the generated suite, "pass rate" would be an invented number. "Selectors provably resolve" is the strongest claim the system can actually support, so it is the one reported.

23Limitations

The project ships a model card (docs/LIMITATIONS.md). The green "passed a syntax check" badge means each generated file passed a static structural check only. It does not mean the tests were executed, that the selectors resolve against your running application, or that the assertions pass.

The same qualification governs the generation success rate of §11, and is the most important sentence to carry away from this report: it is not a pass rate. A suite can score 100 and still fail on its first run — every planned file was written, all of it parses, every selector exists somewhere in the application, and the assertion about what the page does after clicking is still the model's guess. The score measures the quality of the generation, which is the only thing measurable without executing anything, and the API ships that caveat in the payload so no client can display the number without it.

Selector extraction is regex-based

It can miss dynamic classes (className={styles.x}), CSS-in-JS, and some ARIA/role/text selectors, so both false positives and false negatives are possible. Selectors marked "not verified" need review.

Very large repositories

May exceed the model's context window. Low-priority files are summarized rather than sent verbatim, which can reduce selector accuracy.

Output size ceilings

Extremely large suites can hit provider output-token limits. Narrowing the requested scope and regenerating is the workaround.

Free-tier variance

Quality and latency depend on whichever provider was available. Results vary run to run; the provenance report always names the model that actually answered.

Data handling

Repository contents are held only for the duration of a job (SQLite, pruned after 24 hours) and sent to the selected LLM provider. Linked GitHub tokens are encrypted at rest when SESSION_SECRET is set. The security scanner is passive and refuses internal or private targets.

In plain wordsSaying "I checked this much, and no further" is not a weakness in the project. It is the thing that makes everything else it says believable.

What appears to be genuinely unusual

  • A score that refuses to be a pass rate. Every vendor page surveyed leans on confidence language. Shipping not_measured inside the payload, so a client cannot render the number without the caveat, has no equivalent in the field.
  • Push verification by content hash. Unadvertised elsewhere — probably because most tools sync into an existing repository, where a short commit matters less.
  • Credential exclusion before upload. No surveyed competitor advertises detecting and withholding .env and friends at all, let alone client-side.
  • A from-scratch logistic regression for file selection, where the field reaches for an LLM call or a fixed heuristic.

Where the field is ahead

Stated plainly, because a comparison that only flatters is not a comparison. Every serious commercial tool executes the tests — Octomind in the cloud, QA Wolf with human review, Meticulous by deterministic replay. Session recording beats crawling for grounding, because real users reach edge cases a crawl never will. Incremental publishing — a pull request into the repository you already have — is standard elsewhere and absent here. And most of what these products actually sell is maintenance: keeping a suite green as the application changes, where Testra is one-shot.

On the sourcingThis survey rests on vendor pages and third-party comparison sites, several of them written by competitors about each other, and octomind.dev could not be reached directly during the review. Treat the pricing figures as indicative rather than quoted, and verify before relying on any of it commercially.

In plain wordsOther people build this too. The expensive ones actually run the tests, which is the one thing this does not do yet — and the honest way to compete is to say so on the same page as everything it does better.

25Roadmap and future enhancements

Ordered by how much each would change what the system can honestly claim, not by how hard it is to build. The first item is the one that would retire the largest caveat in this report.

Near term — closing the measurement gap

  1. Sandboxed execution. Run the generated suite in Docker against a live target and report real pass/fail. This is the single highest-value item in the document: it converts the generation success rate (§11) from an aggregate of static checks into a measured outcome, and lets the product finally say "these tests pass" — a sentence it currently, deliberately, refuses to say. Everything needed is already in place: the scaffold emits a runnable project with a working webServer block, and the CI workflow it writes is the same command a sandbox would run.
  2. AST-based selector extraction. Replace the regex anchor scan with a real parse, capturing roles, accessible names, visible text and dynamic class expressions (className={styles.x}, CSS-in-JS). This is the largest current source of both false "not verified" flags and missed real ones, and it is the limitation most likely to make a good suite look worse than it is.
  3. Secret scanning with entropy analysis. The current content detector (§12) matches only issuer-prefixed tokens, which is deliberately conservative. Adding a calibrated Shannon-entropy check with a per-file-type threshold would catch bespoke credentials — internal signing keys, self-issued tokens — without the false-positive rate that made a generic api_key = rule unusable.
  4. Verify pushes against a re-read of file content, not only the tree. Content hashes prove the blobs match what was uploaded; they do not prove the branch is what the user will clone if a concurrent write raced ours. Comparing against GET /contents after the ref update would close that window.

Medium term — scale and adaptation

  1. Retrieval-based context selection. Per-provider context budgeting with embedding retrieval over the repository, so very large codebases stop relying on the summarization path that currently degrades selector accuracy.
  2. Re-fit both models on real outcomes. Retrain the logistic regression on which files actually produced verified, low-fragility selectors, and re-fit FEATURE_WEIGHTS from observed selector breakage in real repositories over time. The plumbing for both already exists and is unused only because the outcome data does not exist yet — which sandboxed execution would produce.
  3. Weight the success rate empirically. The four component weights in §11 are reasoned, not fitted. Once real pass/fail data exists, they can be regressed against it, so the score predicts something measured instead of encoding a judgement about which failure hurts most.
  4. Incremental publishing. Push into an existing repository on a branch with a pull request, instead of only creating a new one. This is the most-requested capability the current design cannot express, and it makes the collision handling in §12 load-bearing rather than defensive. It matters most from the CLI (§19), which already runs where the repository is.
  5. A capture extension for the browser. The crawler follows links and application routes; it does not drive the interface, so a modal, a wizard step or a menu that only opens on click is never visited, and its selectors are never grounded (§23). A browser extension would let the user navigate to the exact state they want tested — a cart with three items, step two of checkout — and capture the anchors from the page in front of them, with no credentials handed over at all. The wire format already exists: grounding.index_to_dicts() is what the crawl-first flow already persists, so the writer's crawl-only mode would consume it unchanged.

Longer term — product surface

  1. Diff-aware regeneration. Re-submit a changed version and regenerate only the specs whose grounded selectors moved — turning Testra from a one-shot generator into something that stays attached to a codebase.
  2. Conversational refinement. "Add a test for the forgot-password flow", applied against the existing suite and its grounding index rather than a fresh generation.
  3. Self-healing suites. Re-crawl on a schedule, detect selectors that no longer resolve, and open a pull request repairing them — the self-heal loop of §11 pointed at drift over time instead of at generation-time misses.
  4. Visual selector picking. Screenshot the crawled page, let the user click an element, and ground a test on it directly — the shortest possible path from "test this button" to a grounded assertion.

26Conclusion

Testra takes a task that is universally agreed to be valuable and universally avoided — writing end-to-end tests — and reduces it to pasting a URL. The engineering interest is not that it calls a language model; almost anything can call a language model. It is the apparatus built around the model: a deterministic pre-filter that spends no tokens, a learned classifier that adapts file selection to the codebase in front of it, a grounding layer that traces every generated selector back to the line of source it came from, a repair loop that fixes misses with evidence rather than with another guess, a durability model that grades what will still work next quarter, and a benchmark that refuses to flatter itself with a convenient denominator.

The two ML components embody the project's technical thesis: prefer the small, explainable thing. A 226-line logistic regression with named weights, readable JSON and a safe fallback path is a better engineering answer than a dependency-heavy black box when the model is small, the data is thin, and somebody will eventually need to ask why did it score that file a 9?

In plain wordsA robot that checks your website, written by a robot that read your website — and a receipt showing exactly what was checked, and what wasn't.
